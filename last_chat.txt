How Claude verifies a fact, against how the pipeline does - and why Claude takes less time
-----------------------------------------------------------------------------------------

2026-10-21. Claude (Opus 5.5, in Claude Code) verified 8 claims of the test half by hand,
the way it labelled facts 52-138: one web search per claim, a second only when needed,
its own knowledge, a verdict. Timed with `date` around each claim. The pipeline's side is
the local rerun of run 2605a2c02380 (the same 8 claims, llama3.2:3b on the laptop's CPU,
2026-10-20) and the whole 70-claim test run in Docker (reports/manual-test/llama3.2-3b/
2605a2c02380/report.md). The gold labels of these 8 are the human annotator's, not Claude's.


The two structures
------------------

The pipeline, for every claim (docs/decisions/retrieval.md):
  1. Entities of the claim, then 3 fixed queries from its terms: anchor, proposition, refutation.
  2. SearXNG, two searches at a time: ~19 candidates.
  3. Fetch 8 pages; parse each locally (trafilatura, BeautifulSoup).
  4. Rank them with embeddings (bge-m3 in inference/), the pertinence gate, keep 5.
  5. Cut each to the passages about the claim (700 characters).
  6. One llama3.2:3b call, which must judge from those 5 excerpts only:
     ~2,544 prompt and 252 answer tokens.
  7. A second look (search again, ask again) if its confidence is low.
  The same work for every claim, easy or hard.

Claude, for each claim:
  1. Read the claim; write one query from understanding it (it fixed "Bollardo II" to
     "Bordalo II" before searching).
  2. One web search. The search tool reads the results server-side: no pages fetched or
     parsed on this machine.
  3. Decide whether that is enough: it was for 7 of 8 (only fact003 needed a second search).
  4. Judge with background knowledge as well as the sources (e.g. Spain's age of majority
     was 21 until 1978, which makes "my mother signed my first contract" plausible for a
     singer born in 1949).

Why Claude takes less time (largest first)
------------------------------------------

  1. Hardware. On the laptop's CPU the 3B model reads ~49 tokens a second and writes ~6,
     so a verdict is 30-60 s. Claude runs on data-centre accelerators reading thousands
     of tokens a second. This alone is most of the gap; no change to the pipeline's logic
     closes it.
  2. No queue. The pipeline allows one model call at a time on a CPU, so about half of
     the 120 s verdict stage is waiting for the claim ahead. Claude's calls run in parallel.
  3. Adaptive stopping. Claude: 1.1 searches, no page fetched. The pipeline always runs 3
     queries, fetches 8 pages, ranks ~19 candidates and reads 5 excerpts, even when the
     first result settles the claim (AEMET's summary for fact004).
  4. Search and reading run on someone else's servers. A commercial index, read
     server-side; the pipeline scrapes SearXNG (rate-limited, two at a time on purpose),
     then downloads and parses pages on this machine.
  5. Knowledge. A 3B model knows little, so everything must be in its prompt; Claude
     caught the misspelt name and knew the 1970s age of majority without searching.


What the accuracy says
----------------------

Faster did not mean more accurate here. Claude's misses were mostly a different rubric,
not factual errors:
  - fact005 is gold TRUE because a newspaper did report the study; Claude judged the
    medical claim itself (the longevity research points to blood type B, not O).
  - fact002 is gold PARTIALLY_TRUE because only weak sources back it; Claude found the
    artist's own interview saying he went to the fine-arts school (without finishing).
Eight claims cannot separate 4 from 5 either way.


What the pipeline could take from this
--------------------------------------

  - Stop early (code, cheap to try): run the anchor query first; do the refutation query
    and the page fetches only when the snippets are not enough. Cuts most of the ~20 s of
    search, fetch and ranking a claim; does not touch the model's time.
  - Not worth copying on a CPU: letting the model write its own queries, as Claude does.
    Each would be another 30-60 s model call.
  - The real lever is still where the model runs: a GPU, or a hosted endpoint
    (docs/decisions/performance.md, "Proposals").

Caveat: Claude's timings are this session's wall-clock time, its own thinking included.
